## 2. Authentication and secrets (R-1, R-2)

- **The session token is never visible to the agent.** Like the AI key, it
  lives in the sandbox's outbound layer:
  - testing: an instabox Secret scoped to Alembic's agent endpoint host;
  - production: the sidecar that holds the AI key.
  
  The agent's requests carry a placeholder; the real token is added on the
  way out.
- **The token** is a JWT signed with a **dedicated agent key** (never the
  Supabase JWT secret), with:
  - `typ = "alembic-agent"`, `aud = "alembic-agent-api"`;
  - `{package_id, session_id, job_id, invoker_id}`;
  - `exp ≤ 15 min`, renewed by the orchestrator.

  Every request is refused unless the job is the session's **current
  running** job, and the package matches session, job and changeset.
  Renewal re-checks the invoker's membership. A Supabase user JWT is never
  accepted on these endpoints, and an agent token never works against
  PostgREST: different key, different audience.
- **The fetch proxy refuses:**
  - Alembic's own hosts (including the agent API);
  - private, loopback, link-local and metadata addresses, and Fly
    `.internal` names, checked after DNS resolution and on every redirect;
  - query strings over 512 bytes;
  - any URL containing a known token prefix.

## 3. Sandboxes and isolation (R-3)

- **Production (Fly):** each course's sandbox is its own Machine in a
  dedicated Fly app for sandboxes, with no other services in that app or
  organisation's private network. Machine-level firewall rules drop all
  traffic except to the gateway and the fetch proxy, so private-network
  (6PN) traffic to peer machines is refused too. Volumes are created per
  course and destroyed with the sandbox, never reused.
- **Testing (instabox free plan):** one VM. Each course gets its own Linux
  user and home, with nftables rules per user: only the gateway, the fetch
  proxy and Alembic's agent endpoint are reachable (the latter through the
  Secret injection). Users can't read each other's homes (mode 700). This is
  weaker than one VM per course, and accepted for a handful of known
  testers (O22).
- Claim R.7 tests both: no egress beyond the allowed hosts, **and** no
  reachability of a peer sandbox, the worker, `.internal` or metadata
  addresses.

## 4. Endpoints (Vercel, service role behind token checks)

### 4.1 `POST /api/agent/changesets`

1. Verify the token (§2).
2. Register `changesetId` in `agent_changesets`. A repeat returns the
   existing record (R-12).
3. Check each path with `canWritePath('agent', path, {invoker})`. Harness
   records are allowed; their content is not trusted (§6).
4. Refuse when the course is read-only, the job is cancelled, or the
   session is `paused:owner` or `paused:handout` (A-2).
5. Decide:
   - any file being edited → `pending`;
   - `dependsOn` points at a changeset that is not yet queued → `pending`;
   - else `queue_insert(kind 'changeset', idem = changesetId, invoker =
     token.invoker_id, depends_on = <the dependency's queue row id>)` →
     `queued`.

   A `changeset` row carries `invoker_id` and no `actor_id`.

### 4.2 `GET /api/agent/changesets/:id`

Only for a changeset of the token's package and job (R-9).

### 4.3 `GET /api/agent/changes?since=<path→version>`

Returns, for paths of this course only:
- the working repo head's changed files, with actor and door;
- **this job's own** pending and queued changesets.

It never returns other members' unsynced drafts (`sync` rows) (R-8).

`private/instructor/` content is included: the agent may edit it
(`edit.private`). **Sources are never returned here.** An AI-allowed source
is fetched through `GET /api/agent/sources/:id`, which checks
`canAgent(invoker, 'source.use-ai', {aiAllowed})` against the `sources` row
and returns a signed link valid for 60 s.

### 4.4 `POST /api/agent/events` (R-4)

- `kind` is a closed enum: `message`, `tool`, `progress`, `question`,
  `handover-note`. Payloads ≤ 64 KiB. At most 120 events a minute per
  session. `seq` is assigned by the server.
- A `question` creates exactly one Needs-you item type, **"Question from
  the assistant"**:
  - its text is shown as untrusted plain text (no links, no HTML);
  - its only actions are a free-text or multiple-choice answer.
  
  The agent can't create any other item kind (Approve, Both changed,
  Reconnect GitHub, Publish…).
- **An answer is never an approval, a publish, or a permission grant.**
  Approvals and Tier-3 actions happen only through their own UI and
  endpoints.

## 5. Deferral and pending changes (R-7, A-1)

- **Periodic job:** every 30 s, the orchestrator re-offers pending
  changesets in creation order. One becomes `queued` when none of its files
  is being edited **and** its `dependsOn` (if any) is queued.
- **30-minute bound:** counted from when the changeset became eligible, so
  a dependent's clock starts only once its dependency is queued. The
  dependency always goes first. After the bound, the changeset is queued
  with `fromOpenEditor = false`. A cycle among pending changesets is
  impossible: `dependsOn` must name an already-registered changeset.
- **Removal or cancellation:** the invoker's pending changesets become
  `purged` at once, and their queued rows are refused at execution.
- **Per-path re-check at execution:** the committer re-checks every path
  with the invoker's **current** role (`permitted()` in the committer). A
  deputy whose term ended can't land deputy-only files.

## 6. Agent-authored content (R-5, R-11)

- **The agent may read private instructor files and AI-allowed sources.**

## 7. Session reasons and endpoint behaviour (A-2, A-3)

`reasons ⊆ {working, waiting, paused:owner, paused:handout, paused:github,
paused:budget, unavailable}`.

| Reason | Hand-over | Events | Catch-up |
|---|---|---|---|
| paused:owner, paused:handout | refused | accepted | accepted |
| paused:github | accepted (queued; it waits) | accepted | accepted |
| paused:budget | accepted for the current step; the next step needs `extend` on the job's hold (ledger §9.9) | accepted | accepted |
| unavailable | — | — | — |

**Quick asks** use no sandbox. Vercel calls the gateway with a per-ask key
and a hold on the asker's account. The answer returns to the asker's editor
and goes through the sync path when accepted.

**Automatic jobs** (R-10) run with the rights of the person whose action
triggered them, capped at co-author rights: `canAgent(min(triggerer,
'co-author'))`. They are paid from the course allowance. Owner-only paths
are never written by automatic work.

## 10. Round 2 resolutions (G7 round 2) — these rules take precedence

1. **Keeping the token out of the agent's reach (H6):**
   - **production:** the agent runs as a non-root user with no sudo, `/proc`
     is mounted with `hidepid=2`, and ptrace is disabled (`yama ptrace_scope
     = 3`); the sidecar runs as another user, holding the token and the AI
     key in memory only;
   - **testing (instabox, one VM):** each course's Linux user reaches the
     agent API and the gateway only through **its own local proxy port**
     (nftables owner match → a per-course port), and that proxy holds the
     course's token. No VM-wide secret is used for the session token.
   R.7 also checks that the agent user can't read the sidecar's environment
   or memory, and that one course's user can't use another course's proxy.
2. **Allowed hosts (R-3):** the machine firewall allows the gateway, the
   fetch proxy and the agent API (Alembic's API host, whose addresses are
   resolved and pinned by the orchestrator when the sandbox starts, renewed
   on change). Nothing else.
3. **Re-offering repeats every refusal (R-7):** the 30-second job re-runs
   §4.1 steps 1–4 (token still valid, paths, read-only course, paused
   reasons) before queueing a pending changeset.
4. **Automatic jobs are capped at co-author rights at every check (R-10):**
   the changeset records `rights_cap = 'co-author'`, and both §4.1 step 3
   and the committer's re-check use `min(invoker role, rights_cap)`.
5. ~~**Public records are checked (R-5)** …~~ Superseded (§13): no checks
   at Publish; public records are the type package's, published as they are.

## 11. Round 3 amendments (2026-10-29): the hand-in after foundations steps 1–2

The course contract changed under this spec: package-contract-v3 draft 5
(FD-09/FD-10, §11–§14) and history-v3 draft 2. The agent's changesets now
follow exactly the rules people's writes follow; the agent gets no route of
its own.

1. **File entries are the write path's** (package-contract-v3 §11.2). Each
   `files[]` entry becomes one row entry:
   - **text** (`encoding: utf-8`): `{path, baseVersion, text}`.
   - **non-text** (`encoding: base64`, ≤ 4 MB decoded): the endpoint runs the
     upload route's checks before anything is queued. Those are `fileKind`
     from the active profile, `mediaProblems` (bytes and SVG), the course's
     total, and the rate limits, counted against the **invoker** and the
     course. Then it creates the GitHub blob, records it in `course_blobs`
     (`uploaded_by` = the invoker), and queues a blob reference. So the
     committer's ledger check (K1.10) holds for the agent too.
   - **delete** (`content: null`): the §11.6 rules apply. A listed chapter's
     part files are never deleted (only `removeChapter`), and deleting in
     `private/` needs `delete.private`, which the agent doesn't have.
   - **move** (`movedFrom`): §11.6, checked on both paths, with kind and
     extension kept.
2. **Course operations are proposals, never writes.** `alembic.json` isn't a
   file entry (it is `settings` in the profile's path classes). A changeset
   may carry `courseOps: [<operation>]` (contract §13.1 shapes, checked by
   `parseCourseOp`):
   - each becomes a Needs-you **approve** item for the owner and deputy;
   - on approval it is queued as a `courseop` row with the **approver** as
     actor, so the usual re-check at execution applies;
   - `setLicense` goes to the owner only.
3. **Restores** are ordinary text or blob entries carrying the old content.
   The agent gets no `restore` rows; the version rule treats them like any
   edit.
4. **Content safety is the same as for people.** The SVG check runs on every
   write. Raw HTML in Markdown is published only as a clean copy (K1.20); the
   agent's text is the main reason that exists. ~~The answer-key and copying
   checks apply at Publish (§6).~~ (Superseded, §13.)
5. **Paths come from the active profile** (FD-10). Harness records sit at the
   profile's records folder (Coursewerk OER: `private/coursewerk/`); its
   server-only notes (`serverOnlyFiles`) are refused. (Under the site type
   contract: the definition's `records` folders and `fixed` entries.)
6. **History and Needs you:**
   - changeset commits read "the assistant, for <invoker>" (H.1: the
     `Alembic-On-Behalf-Of` trailer on Alembic's own commits);
   - a changeset file that ends **both changed** raises the usual item with
     the version not on top, offering "Use the other version" (history-v3 §4).
7. **Budget:** binaries in a changeset count toward the invoker's and the
   course's upload limits, so a looping agent can't spend the owner's GitHub
   budget faster than a person could.

**Claims (round 3):**
- **R.20** A changeset's non-text entries pass the upload checks and enter the
  ledger before they are queued; a changeset can't place a blob a person
  couldn't.
- **R.21** A changeset never writes `alembic.json`. Its course operations
  become approve items, queued only as the approver.
- **R.22** A changeset can't delete a listed chapter's part or anything in
  `private/`, and moves follow the contract.

## 13. Alignment with the site type contract (2026-10-30)

The owner's rulings of 2026-10-30 and the site type contract (family
`docs/SITE-TYPE-CONTRACT.md`) change this spec:
- **No content checks at Publish.** The answer-key and copying checks, and
  the "publish profile" that wrote checked public records, are gone (§6,
  §10.5, §11.4, L5 above are marked superseded). The person publishes what
  they marked completed; the type package's workflow (Coursewerk) carries
  its own checks, approvals and reviews while the author works.
- **Records:** the type package's tools write both `records` folders through
  this hand-in; the public one is published as it is. Records are **never
  combined**: a record whose base version isn't current refuses the whole
  changeset (the tools retry), because a hash-chained log can't have two
  tops (Coursewerk's review, 2026-10-30).
- **Records budget** (Coursewerk's request): record files are exempt from
  the 50-files-per-changeset cap (§12 M6) up to 200 record files per
  changeset; each record file at most 4 MB; `.jsonl` is accepted under
  `records`; a site's records stay under 50 MB in total (the hand-in refuses
  more and says so).
- **What the tools may read:** `alembic.json` (units, statuses, licence,
  details) through catch-up, and the person's own words with their identity
  (answers to the assistant's questions and chat messages, tagged with the
  person and the event seq). Alembic derives nothing from them (§4.4).
- **Outside Alembic:** inside an Alembic site the type package's tools work
  only through this hand-in; pushes to the `records` folders made on GitHub
  are undone. A package made outside Alembic is brought in once.


## 14. What the type package's assistant needs (Coursewerk's review, 2026-10-30; G7 round 4 resolved)

From Coursewerk's GenChem re-evaluation (its report §4). Each is mechanism, the
same for any type package; none lets Alembic judge, gate or warn. Claims R.23–R.27.

1. **Questions in one item (R.23).**
   - **Transport:** a hand-in may carry `digest: { questions: [{ id, text ≤ 500 chars, choices? ≤ 6 of ≤ 120 chars, recommended? }] }`, at most 50 questions. It raises **one** Needs-you item of kind `question` (with `digest: true`), addressed to the invoker; §4.4's event kinds are unchanged.
   - **Answers:** only the addressee answers. Partial answers are kept. "Accept all recommended" records, for each question that has a recommendation, that choice with `via: "accept-all"`; questions without one stay open. An answer is never an approval of anything in Alembic. The answers (with the person and the event seq) reach the assistant through catch-up for the same session.
   - **Bounds:** one open digest per job; at most 20 open question items per invoker (further ones wait); an open digest is withdrawn after 7 days or when the invoker leaves the course.
2. **Who changed what (R.24).** Catch-up takes a commit that must be an ancestor of the head, and returns, for each file changed since **that the invoker may read**, the commits and their people as History shows them (combined section edits name both). At most 300 files and 50 commits per file, and 1 MB per answer; over that, "too much changed: read the files".
3. **Cost shown first (R.25).** A job states an estimate; the person sees it with Start / Not now. **The hold is the estimate:** a job that reaches it pauses (`paused:budget`), and going on needs the person again. An "always for jobs under N credits" setting is the invoker's own, compared with the hold, and spends the invoker's allowance.
4. **Reference texts (R.26).** The assistant may read an uploaded source only when the **invoker could open it themselves** (their own upload, or shared with the course), it allows AI use, and it isn't removed. This is checked again on every read, served through the existing short-lived signed link. A PDF's text is made on upload in a separate process with time, page and size limits; a scanned or failing PDF has "no text". The text copy follows the source's flags and never enters the repository. Web pages that need a browser are uploaded by the person as PDF or text.
5. **Records in bulk (R.27).** A **records-only** hand-in (every entry a text write under a `records` folder, no course operations, deletes, moves or figures) skips only the 30-minute wait for a typing person. It still goes through the queue and the committer's re-check (rights cap, read-only course, paused states). A mixed hand-in waits as a whole. Records are never combined (§13). Rate: at most 30 records commits and 20 MB of records per job per hour. Order: first in, first out across the job's records hand-ins, `dependsOn` honoured.

**Public records and "only completed pages are published"** (G7 round 4, item 10): the public records folder is published as it is (contract §5, G0 round 3). To keep that carve-out small, the type definition's public records are limited to 1 MB in total and to the kinds the type package declares (Coursewerk: `ATTRIBUTION.md`, `CHECKED.json`). Taking the folder off the website remains the person's ("withdrawn"). Recorded for the owner to confirm (family contract §13).

Coursewerk's two notes for the owner were answered: the optional course setting
"an edit returns a completed page to draft" is built (claim K1.26); a page set
back to draft keeps its last published version by the owner's ruling (A), and
"take it off the website" is the complete retraction.

## 15. Round 5 resolutions (G7 round 5, 2026-10-31): these take precedence over §11–§14

Verdict: pass with fixes. Each fix below is either text (it holds now) or a **C4 entry condition** (code that C4 lands
first, with a claim). Nothing here adds a content check (FD-09/FD-10).

**Records (H1, H2, L6, M2, M3, simplifications 1–2).**
- One predicate, `isRecordsPath(def, path)`, covers both of the definition's `records` folders (private and public);
  nothing hard-codes `private/coursewerk/`. People have no edit action on either (the contract's "people never edit
  either"); only the type package's tools write them, through the hand-in, as text. *C4 entry condition* (today the public
  folder is a lead-editable course file and the private one is checked by a fixed path).
- Records are never combined. A record whose `baseVersion` is stale refuses the whole changeset (the tool reads and sends
  again). Content in the same changeset otherwise lands by the version rule (§11.6). **`bounced` is retired**: a
  both-changed content file raises the usual "both versions kept" item and lands; it never sends records back.
- No "records-only fast path" class. The wait of §4.1 applies only to files open in an editor, and records are never
  open in one, so a records changeset simply runs in queue order with the stale-base refusal.
- `.jsonl` records may be sent as `{path, baseVersion, append}` (text appended, never combined, refused if stale), so a
  log is never rewritten whole. One hand-in body carries at most 4 MB of record text; the hourly rate of R.27 counts the
  bytes sent, so appends cost what they add. The site-wide 50 MB records total stays.
- The public records limit (1 MB in total) is checked at hand-in only, never at Publish. Kinds are the ordinary text
  kinds unless the schema later gains `records.publicFiles` (open point added to contract §13).

**Limits (M1).** §12 M6's limits are per changeset (50 files, 40 MB of blobs); records do not count toward the 50.

**Re-check at execution (M4, L5).** A changeset with records needs, when it runs, the invoker still to be an editor
(rights capped as in L7), the course not read-only, and the session not `paused:owner` or `paused:handout`. *C4 entry
conditions:* these in `permitted()`, the rights cap (L7), and the `restoreChapter` ancestor check (M7).

**The digest (M5, simplification 3).** One rule: a digest is raised when the changeset is received (independent of
whether its files land or wait), deduplicated by `changesetId`, and there is at most one open digest per invoker per
course: a new one replaces the questions still unanswered in the old one. The 20-item cap counts §4.4's single
questions too; over it, new questions are refused (the tool is told), never queued. Question ids are unique, ≤ 64
characters; a `recommended` answer must be one of the `choices`.

**History (M6).** Each commit names its own row's person. A combined edit names the other person too once History reads
the `Alembic-Kept` pair (later). A version the tool sends that History can't place → "too much changed: read the
files". R.24 replaces §4.3's `since=<path→version>`.

**Cost (M7).** Automatic jobs hold their estimate on the course allowance; the "always under N" setting doesn't apply to
them; a paused automatic job waits for the owner. Automatic starts are at most N credits a day per invoker (N in the
course's AI settings).

**Smaller (L1–L4).** Sources: R.26 replaces `canAgent(invoker,'source.use-ai')` (the uploader, or shared with the course
and AI allowed, not removed); PDF text is at most 2 MB per source and 20 sources per job. `agent_changesets.status` is
`proposed | queued | done | refused | failed`. When a job ends normally its pending content changesets stay queued and
are offered again in the session's next job (fail closed only when the token was revoked). A `setStatus` draft ⇄
completed proposal goes to the invoker (an editor action, contract §6); `withdrawn` and back stay with the lead.

## 16. The harness (owner, 2026-10-31)

Alembic runs no particular harness. C4 starts a type package's command in the sandbox with three things: the gateway key
(a short-lived virtual key), the job budget, and the hand-in endpoint with the job token. Everything the job produces comes
back through the hand-in; every question through the digest (§14, §15). The first harness is Claude Code headless running
Coursewerk's skills; Coursewerk's own `coursewerk-agent` (on pi) replaces it once complete and once an evaluation on real
course tasks favours it (DecisionLog 2026-10-31). Production sandboxes: Fly Sprites; instabox stays a working second
provider.

## 17. Step 3a spike (2026-10-31): what the first live run taught

Claude Code 2.1.288 ran headless in the instabox sandbox as the course's own Linux user (mode-700 home, nftables:
DNS and the testing host's addresses on 443 only; no sudo; other hosts, api.anthropic.com and the metadata address
refused), read `study-guide/atoms.md` through `/api/agent/file`, handed in `spike-atoms-0001`, and the committer
landed it (`e2e9e1a`). 9 turns, 12 gateway calls, 33 credits ($0.33; Claude Code's own estimate $0.19: check the
gateway's Sonnet 5 rates against the invoice). Rules for the orchestrator (step 3b):

1. **One public host.** The sandbox reaches the AI through `/api/agent/ai/v1/messages`, a pass-through to the VM's
   gateway (which keeps every check). Cloudflare's Bot Fight Mode challenged the sandbox (owner turned it off for
   orz.how; a WAF skip rule covers `/api/agent/`). Production will need the same for its host.
2. **Betas.** The gateway passes exactly the four billing-neutral betas the harness sends (claude-code,
   interleaved-thinking, effort, mid-conversation-system); any other is refused. A new Claude Code release may add
   one: the orchestrator pins the harness version, and the gateway's refusal names the beta.
3. **Output cap.** The harness runs with `CLAUDE_CODE_MAX_OUTPUT_TOKENS` ≤ the gateway's cap (8000 in the spike).
4. **Hold size.** The gateway's worst case counts each request byte as a token, so one Claude Code call (≈ 170 KB of
   tools and prompt) is bounded at ≈ 50–75 credits while actually costing ≈ 1–12. A job's hold must exceed one call's
   bound (≥ 100 credits for Claude Code); the estimate shown to the person (R.25) should be the realistic one.
   Open: a tighter bound (count_tokens before the call, or a measured bytes-per-token ratio for the harness's prompt).
5. **Secrets per course user.** instabox's placeholder file is readable only by the sandbox's own user; the
   orchestrator copies the two placeholders into the course user's mode-600 env file. On the shared free-plan VM
   the proxy swaps a placeholder for any local user (accepted for testing, O22; production: one sandbox per course).
6. **Settings that keep the harness quiet:** `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_TELEMETRY`,
   `DISABLE_ERROR_REPORTING`, `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`; the tools allowed are the `alembic` helper,
   `jq`, `cat`, Read and Write (no network tools).
